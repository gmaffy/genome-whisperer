The 512 Mb Ceiling

Onion and pepper contigs are longer than any BAM- or VCF-style index can address. Here is what breaks, how to recognise it in ten seconds, and what changed in the pipeline.

Affects onion · pepper Stage AlignReads / BQSR Written 24 Aug 2026
536,870,911 The highest coordinate a BAI, TBI or CRAI-derived index can address — 229−1.
against
1,056,413,696 The length of a single contig in GCA_030765085.1, our working onion reference. Fifteen of them.

Why the number is fixed

Nothing about it is tunable, and no newer version of the tools raises it.

A BAI-style index carries a linear index: a flat array of 215 windows, each covering 214 bases. That product — 536,870,911 — is the entire addressable span of one reference sequence. A feature beyond it has no window to live in, so the write walks off the end of the array.

The same binning scheme backs three formats we rely on: .bai for BAM, .tbi for bgzipped VCF, and the in-memory index htsjdk builds when it opens a CRAM. All three inherit the ceiling. The exception is always the same shape:

java.lang.ArrayIndexOutOfBoundsException: Index 36621 out of bounds for length 32770

Both numbers are readable. 32770 is the array size — 229 ÷ 214, plus two — and it is the same in every one of these failures, so it is the fingerprint. 36621 is the window the offending feature wanted, so multiply it by 16,384 to recover the coordinate: position ≈ 600,014,848.

Worth knowing: the first shard that failed on ON1708 reported Index 32770 — window 32770, or roughly base 536,903,680. The read that took down the run was about 33 kb past the line.

Three places it bites

One limit, three symptoms, and they surface at different moments — which is why fixing the first only reveals the second.

WhereWhat happensFails at
Reading a CRAM htsjdk has no CRAM index reader. When a .crai sits beside the file it converts it into an in-memory BAI — CRAMBAIIndexer.processBAIEntry — and overflows. Engine startup, before a single record is read.
Writing a VCF GATK writes a .tbi alongside any .vcf.gz output, through TabixIndexCreator. Same binning, same overflow. close() — the call finishes, then throws away the work.
Writing a BAM index ApplyBQSR would emit a .bai. Already handled: --create-output-bam-index false, then a CSI built separately. Handled before this investigation.
Intervals are not the trigger. It is tempting to blame -L, since the scatter path queries by interval. It isn't that. htsjdk resolves the index when it constructs the reader, so an indexed CRAM throws with no -L at all. The only way to read one is to have no index — which the scatter cannot do.

What to use instead

For each thing GATK needs, exactly one format survives.

You needDoes not workWorks
Reads GATK can index CRAM + .crai — converted to BAI on open BAM + .csi
Variants GATK can read .vcf.gz + .tbi — cannot be built
.vcf.gz + .csi — builds, but GATK will not read it		 .vcf + .idx (Tribble)

That second row is the one that costs time. A CSI index has no coordinate ceiling and bcftools index -c writes one happily — but GATK does not accept CSI for variants, and says so misleadingly:

A USER ERROR has occurred: An index is required but was not found for file ks.vcf.gz.
Support for unindexed block-compressed files has been temporarily disabled.

The index is right there. GATK simply cannot read that kind. Dropping the compression and letting GATK write its own Tribble .idx is the only combination that both builds and reads.

Which of our genomes trip it

Everything we grow sits comfortably under the line except two crops — and those two are over it by a factor of two to four.

Diagnosing it in three commands

If a GATK step dies on a new species, this is the order to check things.

  1. Measure the longest contig

    Anything above 536,870,911 means every index decision below changes.

    sort -k2,2nr ref.fa.fai | head -1

  2. Confirm the fingerprint

    Search the stack trace for length 32770. That constant appears in no other failure. CRAMBAIIndexer in the frames means reads; TabixIndexCreator means variants.

  3. Prove it is the index, not the data

    Move the .crai aside and rerun without -L. If it now works, the file was never the problem — the index beside it was.

    mv sample.cram.crai /tmp/ && gatk CountReads -R ref.fa -I sample.cram

What changed in the pipeline

All of it keys off one predicate, so genomes under the ceiling are untouched — same plan, same steps, same formats.

alignmentdir/scatter.go

refExceedsBaiLimit() reads the .fai and decides everything downstream. gatkReadsNeedBam() and variantSuffixes() derive from it, so reads and variants can never disagree about which reference they are on.

alignmentdir/dirAlign.go

A new materialize_rgmd_bam step decodes the CRAM back to a CSI-indexed BAM when that is the only surviving alignment. The bootstrap chain's seven VCF paths follow variantSuffixes. The run announces the decision up front.

alignmentdir/refcheck.go new

Catches a contig-name mismatch during the scan and names the fix, instead of letting it surface hours later as a missing-sequence error from inside htslib.

alignment/helper.go

CramToBam() and RgmdBamPath(). Also corrects a comment that claimed .crai escapes the limit — true of the format, false of GATK, and the assumption this whole class of failure hid behind.

utils/utils.go

ValidateGvcf looks for .tbi or .idx according to the file it was handed, rather than assuming bgzip.

scripts/reheader-crams.sh new

Repoints CRAMs at a renamed reference. Verifies before it writes, refuses anything that is not a pure rename, keeps the replaced header, and is safe to run twice.

scripts/run-local.sh

Peak-disk estimate raised from 4× to 6× the staged bytes, because an affected sample now also holds the decoded BAM.

The cost, honestly

On an affected reference a resuming sample decodes its CRAM to a BAM once — roughly twice the CRAM in disk, deleted at that sample's cleanup. A sample aligned from scratch pays nothing: MarkDuplicates already wrote the BAM, and converting it to CRAM does not delete it, so the plan just indexes what is already there.

If disk gets tight, the cheaper shape is to slice per shard — extract each interval into a small BAM with samtools, which reads the .crai without complaint, capping peak at one shard instead of a whole BAM. More moving parts, which is why it is not the default.

The trap sitting behind it

Unrelated to the ceiling, but it surfaces the moment the ceiling is cleared, so expect both together.

Our onion CRAMs were aligned against the GenBank-named reference (CM060928.1). The assembly directory now holds a renamed copy (chr1_0-1056413696). Same sequence — all 2,099 M5 checksums and lengths match, in order — but CRAM resolves its reference by contig name, so nothing could decode them:

[W::cram_get_ref] Reference file given, but ref 'CM060928.1' not present
[E::refs_load_fai] Failed to open reference file '/mnt/u/Genomes/Onion/...fna.gz'

It falls back to the UR: path baked into the header at alignment time, which had long since gone. Because the sequences were provably identical, the fix was a header rewrite rather than a realignment — and it turned out to be nearly free. Dropping the dead UR: field more than paid for the longer contig names, so the new header fits inside the old one's footprint and samtools pads it in place:

scripts/reheader-crams.sh -r assembly/..._corrected.fa -d /mnt/v/DATA/onion
Nothing after the header moves, so existing .crai files stay byte-identical and no reindex is needed. Five 40–80 GB CRAMs migrated in seconds rather than hours. Verify with M5 first — if the checksums differ it is a different assembly, not a rename, and the script will refuse.

Still open

variants/createGvcfs.go hardcodes .g.vcf.gz, and a per-chromosome gVCF on a 1.06 Gb contig needs exactly the .tbi that cannot be built. CreateGvcfs will fail the same way on onion and pepper.

It was left alone deliberately: changing the gVCF format pulls in the naming convention, GenomicsDB import and MergeGvcfs together, and that is a decision worth making on its own rather than folding into a BQSR fix. Whoever picks it up should start from the format table above — the same three options, the same single survivor.

Verified end to end on a real sample through all six pipeline steps — index, decode, bootstrap known sites, both recalibration passes, ApplyBQSR, conversion and cleanup — with no overflow at any stage. The .crai-hidden test and the CSI-VCF rejection above were both reproduced directly against GATK 4.6.2.0 / htsjdk on the same reference.
